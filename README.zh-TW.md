# neko-auth

---

雙重驗證碼從不離開你的電腦。一個命令列驗證器，資料存在本機加密的保險庫裡，
用一個電子郵件加一個密碼解鎖 —— 而這兩樣東西哪裡都沒有保存。

## 這東西是做什麼的

雙重驗證的金鑰存進本機一個加密的 SQLite 保險庫。不同步、不上傳，也沒有帳號
要登入。全程唯一會開啟網路連線的指令是 `update`，而且只在你主動執行時。

```
$ neko-auth
電子郵件：zoe@example.com
主密碼：

neko-auth 0.1.0
保險庫：~/.local/share/neko-auth/vault.db
閒置 300 秒後自動鎖定
輸入 `help` 查看指令，`exit` 離開

neko-auth › get github
GitHub (zoe@example.com)
  123 456   █████████░░░ 22 秒
```

## 威脅模型

這一節是整份 README 最重要的部分。在把任何東西交給它之前，請先讀完。

**neko-auth 保護什麼。** 保護**靜態的**保險庫：筆電被偷、備份被拷走、`.db`
檔案被人從硬碟上撈走 —— 也就是 neko-auth 沒在執行的時候。這就是威脅模型，
而且這就是全部的威脅模型。

拿到你保險庫檔案的攻擊者，能知道的只有**裡面有幾個帳號**。發行方、帳號名稱、
金鑰、演算法、位數、週期、時間戳記全部是密文，而且密文做了填充，長度也不會把
名稱洩露出去。猜一次憑證的成本是一次完整的 Argon2id 運算 —— 檔案裡沒有任何
更便宜的驗證點。

保險庫要用**一個電子郵件和一個密碼一起**解鎖，而**兩者都不在檔案裡**。不存
信箱，也不存信箱的雜湊。拷走保險庫的人必須把兩半都猜對，而檔案不會透露任何
一半的線索。代價在下面寫清楚了：信箱打錯和密碼輸錯是同一個錯誤訊息，而忘了
當初用的是哪個信箱，和忘記密碼一樣，保險庫就永久打不開了。

**neko-auth 不保護什麼。**

- **惡意軟體，或任何以你的身分執行的行程。** 它可以直接讀這個行程的記憶體
  （`ptrace`、`task_for_pid`、`ReadProcessMemory`）。任何使用者空間的程式都
  擋不住。
- **root 或核心層級的攻擊者。** 同理，而且更甚。
- **被換出到 swap 的金鑰。** 我們不做 `mlock`：Linux 上 `RLIMIT_MEMLOCK`
  常常只有 64 KiB，`VirtualLock` 受工作集配額限制，而且兩者都撐不過休眠。
  鎖一個你鎖不住的記憶體分頁，是虛假承諾而不是防護。**請使用全碟加密** ——
  FileVault、LUKS、BitLocker —— 並替 swap 也加密。
- **系統當機傾印。** 我們在啟動時停用了 core dump，但 macOS 的 ReportCrash、
  Windows 錯誤報告和 systemd-coredump 不在我們控制範圍內。
- **有人把你的保險庫還原到一個真正完整的舊副本。** 保險庫層級的簽章能抓到被
  刪除的列、被插入的列，以及「舊檔案拼上新列」，但要偵測整體還原需要檔案之外
  的狀態，這個工具沒有。
- **你的剪貼簿。** `get -c` 會把驗證碼放到一個所有以你身分執行的行程都能讀的
  地方，作業系統還可能把它同步到你的其他裝置上。15 秒後會清空，但那是緩解，
  不是防護。*（macOS 的 `org.nspasteboard.ConcealedType` 和 Windows 的
  `ExcludeClipboardContentFromMonitorProcessing` 這兩個隱私提示位**目前沒有
  設定**；要設它們得繞過跨平台剪貼簿函式庫直接呼叫原生 API，會和它自己的
  開關剪貼簿操作產生競爭條件。）*

**記憶體抹除是盡力而為。** 金鑰材料放在會自我抹除的緩衝區裡，用的是 volatile
寫入加編譯器屏障 —— 這是 stable Rust 上能拿到的最強保證。但它抹不掉暫存器溢位
和最佳化器已經產生的中間副本。

**沒有任何找回機制。** 信箱和密碼任何一個忘了，那個保險庫裡的帳號就永久沒了。
請做加密備份。

## 安裝

**macOS、Linux、WSL：**

```bash
curl -fsSL https://raw.githubusercontent.com/zoefix/neko-auth/main/install.sh | sh
```

**Windows PowerShell：**

```powershell
irm https://raw.githubusercontent.com/zoefix/neko-auth/main/install.ps1 | iex
```

**Windows CMD：**

```
curl -fsSL https://raw.githubusercontent.com/zoefix/neko-auth/main/install.cmd -o install.cmd && install.cmd
```

安裝指令碼會下載適合你這台電腦的發布版本，比對公布的校驗和，把它加進 PATH，
然後就結束了。它不會建立保險庫，也不會問你任何問題。開一個新終端機，然後：

```bash
neko-auth init
```

把指令碼用管線交給 shell，等於執行那個網址回傳的任何東西，所以你想先讀一遍也
完全合理 —— [install.sh](install.sh) 大約一百行。`NEKO_AUTH_INSTALL_DIR` 可以
改安裝位置，`NEKO_AUTH_NO_PATH=1` 則讓它不要動你的 shell 啟動檔案。

### 從原始碼建置

```bash
cargo install --git https://github.com/zoefix/neko-auth
```

產物是一個靜態執行檔，沒有執行時相依；SQLite 是編譯進去的。如果不想要 QR code
圖片解碼（它會引入 `image`，一大片解析程式碼面）和自動更新：

```bash
cargo build --release --no-default-features
```

## 開始使用

```bash
neko-auth init            # 建立保險庫，設定電子郵件和主密碼
neko-auth                 # 進入互動式工作階段
```

### 從 Google 驗證器搬過來

1. 在 App 裡：**⋮ → 轉移帳戶 → 匯出帳戶**，選好帳號，讓它顯示 QR code。
2. 每張 QR code 都截圖。**帳號多的時候會分成好幾張** —— 全都要截。
3. 一次性全部匯入：

```bash
neko-auth import qr part1.png part2.png part3.png
```

部分匯入會被拒絕。給它三張裡的兩張，它會明說還差哪張、而且什麼都不存，
而不是讓你以為已經遷移完成、其實大部分帳號還只在手機上。

4. **在刪掉手機上的任何東西之前，先核對。** 把幾個驗證碼並排比一遍：

```bash
neko-auth watch
```

只有在驗證碼完全一致之後，才考慮移除手機上的 App —— 而且即便到那時，
在第二台裝置上留一份，通常也比只有一份更明智。

### 其他匯入方式

```bash
neko-auth import uri            # 在不回顯的提示下貼上 otpauth:// 連結
neko-auth import file list.txt  # 一個裝著 otpauth:// 或遷移連結的檔案
neko-auth add                   # 手動輸入網站「無法掃描？」給的那串 Base32 金鑰
```

金鑰永遠不接受作為命令列參數。`argv` 透過 `ps` 對本機所有行程可見，
而且非互動呼叫還會把它留在 shell 歷史裡。

匯出用的 QR code 很密集 —— version 20 起跳 —— 而解碼器的二值化對每個模組佔
幾個像素很敏感，所以一張手機能秒讀的截圖，在原始解析度下可能解不出來。因此每張
圖都會先按幾種縮放比例重試再放棄。如果還是讀不出來，把截圖裁到只剩 QR code
再試。

## 指令

下面每一條在工作階段裡和作為一次性指令都能用。

| | |
|---|---|
| `ls [樣式]` | 列出帳號及其目前驗證碼 |
| `get <名稱> [-c]` | 顯示某個驗證碼；`-c` 同時複製到剪貼簿 |
| `watch [樣式]` | 全螢幕即時看板，帶倒數計時 |
| `add` | 在不回顯的提示下新增帳號 |
| `import uri｜qr｜file` | 從連結、QR code 圖片或檔案匯入 |
| `rm <名稱>` | 刪除帳號，需確認 |
| `rename <名稱>` | 修改帳號的發行方或標籤 |
| `show <名稱>` | 查看某個帳號的參數，不含金鑰 |
| `reveal <名稱>` | 列出帳號的金鑰；需要手動輸入 `REVEAL` |
| `export encrypted <路徑>` | 寫出加密的 `.nekobak` 備份 |
| `export plain <路徑>` | 寫出明文 `otpauth://` 連結；需要手動輸入 `YES` |
| `restore <路徑>` | 從加密備份匯入 |
| `passwd` | 修改電子郵件與主密碼 |
| `doctor` | 檢查保險庫是否損壞 |
| `config [鍵] [值]` | 查看或修改設定 |
| `lang [代碼]` | 查看或切換介面語言 |
| `lock` | 立即從記憶體中抹除金鑰 |
| `update [--check]` | 檢查新版本（唯一會連網的指令） |

每條指令都接受前導 `/`，所以 `/help` 和 `help` 一樣能用。

工作階段裡 Tab 可以補完指令和帳號名稱，歷史**只保存在記憶體中**。
`show coinbase` 本身就是敏感的中繼資料 —— 它說明了你在哪些服務上有帳號 ——
沒有理由活過本次工作階段。

### 備份

```bash
neko-auth export encrypted ~/vault.nekobak
```

`.nekobak` 是一個自我包含、帶版本號的加密封存檔，刻意不是 SQLite 檔案的副本：
備份應該活得比產生它的 schema 更久，最好也比這個程式更久。它的位元組配置寫在
[`src/export.rs`](src/export.rs) 開頭，詳細到足夠用大約五十行程式碼重新實作。

`export plain` 把你的金鑰寫成普通的 `otpauth://` 連結。它存在，是因為那是
**你的**金鑰、你必須能帶走 —— 但它會要求你手動輸入 `YES`，檔案權限 `0600`，
並提醒你用完立刻刪除。

### 離開

`export plain` 產出的連結任何其他驗證器都能接受。這裡沒有鎖定。

## 關於電子郵件

保險庫的金鑰由信箱**和**密碼共同衍生，而不是只由密碼衍生：

```
Argon2id( "neko-auth/identity/v1" ‖ len(信箱) ‖ 信箱 ‖ len(密碼) ‖ 密碼 , salt )
```

每一段都帶長度前綴。直接串接會產生要命的歧義：`("a@b.com", "xyz")` 和
`("a@b.co", "mxyz")` 接起來是同一個字串，那樣其中一組憑證就能打開用另一組
建立的保險庫。

信箱**不保存在任何地方** —— 這正是它的全部意義。保存它，哪怕只保存雜湊，
都等於把一半的祕密交給拷走檔案的人，而且那樣它就不比檔案裡已有的 32 位元組
隨機鹽更有用。

**信箱在輸入時會回顯，密碼不會。** 這個不對稱是刻意的。保護保險庫的是信箱
**不在檔案裡**，這一點跟它是否出現在螢幕上無關。隱藏它只能防偷看螢幕 ——
不在上面那個威脅模型裡 —— 卻要付出實實在在的代價：兩半都看不見的時候，
信箱打錯既無法在打錯的當下察覺，之後也永遠和密碼錯誤無法區分。
`neko-auth init` 完成後還會把正規化後的信箱回顯一次，因為那是你唯一能看到
保險庫究竟期待什麼的時刻。

如果你更想讓它隱藏，`config hide_email true` 可以還原，那時設定階段會改成
問兩遍，而不是靠你用眼睛核對。

在決定用它之前，值得知道的幾件事：

- 信箱錯和密碼錯給出同一個錯誤訊息。這不是故弄玄虛：驗證標籤確實無法分辨是
  哪一半錯了。
- 信箱在使用前會去掉頭尾空白並轉小寫，所以 `Zoe@Example.com` 和
  `zoe@example.com` 是同一個。RFC 5321 確實規定本地部分大小寫敏感；但沒有任何
  電子郵件服務商真的這麼做，而一個打不開的保險庫是遠比理論上的不一致更糟的
  結果。
- **把你用的是哪個信箱寫下來**，和備份放在一起。它是祕密，所以請放在你放密碼的
  地方 —— 但它比你特意想出來的密碼更容易記錯。

`.nekobak` 備份預設有自己獨立的一個密碼，因為它是一個獨立的檔案。
`export encrypted --same-password` 會改用你解鎖時那組信箱和密碼來加密它。

## 語言

neko-auth 支援 English、简体中文、繁體中文 和 日本語。預設跟隨你的系統地區設定，
所以在一台設成日文的電腦上，它開箱就是日文。

```bash
neko-auth --lang zh-Hant          # 只影響這一次
neko-auth config language ja      # 記住
```

或者在工作階段裡：

```
neko-auth › lang
neko-auth › lang zh-Hant
```

可用的值是 `auto`（跟隨 `$LC_ALL`、`$LC_MESSAGES` 或 `$LANG`）、`en`、
`zh-Hans`、`zh-Hant` 和 `ja`。POSIX 地區名稱也能用，所以
`--lang zh_TW.UTF-8` 會按你預期的那樣運作。

繁體中文用的是台灣用語（檔案、設定、網路、金鑰），而不是從簡體逐字轉換 ——
後者正是這類在地化最常見的出錯方式。

有兩處刻意保留英文：

- 確認危險操作時要輸入的詞 —— `YES` 和 `REVEAL`。它們是固定的權杖；翻譯只會
  多出一種打錯不可逆操作的方式。
- clap 自己的參數解析錯誤（「unexpected argument」之類）。neko-auth 輸出的
  一切都翻譯了，包括 `--help`，但函式庫內部的字串搆不著。

新增一種語言，就是在 [`src/i18n/messages.rs`](src/i18n/messages.rs) 的每一條
下面加一行。巨集要求每條訊息都有全部語言，所以漏譯是編譯錯誤，而不是某條悄悄
退回英文。

## 它是怎麼運作的

### 金鑰層級

```
信箱 + 密碼 ─Argon2id(salt, m/t/p)──▶ KEK
                                       │
                                       └─ 解開 ─▶ DEK（隨機產生，密文存檔）
                                                     │
                                   ┌─────────────────┴─────────────────┐
                                 欄位金鑰                           中繼資料金鑰
                              逐欄位加解密                       保險庫完整性簽章
```

兩層的存在是為了正確性，不是速度。修改憑證只需在一個交易裡重新包裝 32 位元組，
這是不可分割的。重新加密整個保險庫不是，而一次做到一半的修改就是一次資料遺失
事件。

**驗證就是解開 DEK，此外什麼都沒有。** 憑證錯了就得到錯的 KEK，AEAD 標籤驗證
失敗。檔案裡刻意不存密碼雜湊，也不存信箱雜湊：前者是這類工具的經典錯誤 ——
一個比它要保護的 Argon2id 便宜十億倍的驗證點 —— 後者則會把一個原本磁碟上根本
沒有的祕密送出去一半。

同樣刻意**不做錯誤次數計數、不做自毀**。攻擊者是拷走檔案離線破解的，我們的
計數器在那邊根本不會執行。這種功能唯一能做到的，就是給你一個親手毀掉自己雙重
驗證的方式。

### 加密

- **Argon2id**，預設 256 MiB / 3 輪 / 4 通道（`--kdf-profile interactive`
  是 64 MiB，`paranoid` 是 1 GiB）。參數存在檔案裡，因為它們是雜湊函式的一部分
  —— 在一台電腦上建立的保險庫必須能在另一台上開啟。讀回時會做上下界檢查：
  `argon2` 自己不做上界檢查，所以否則的話，把儲存的 `m_cost` 改一個位元組
  就是一次記憶體耗盡當機。
- **XChaCha20-Poly1305** 用於每個欄位。192 位元的 nonce 是隨機 nonce 無條件
  安全的原因。AES-GCM 的 96 位元 nonce 會把你推向計數器，而計數器在一個可以
  從備份還原的資料庫裡是個陷阱：還原上個月的副本、再加兩個帳號，你就重複用了
  一個。GCM 的 nonce 重複使用會洩露驗證金鑰本身。
- **每個密文都繫結到它所在的位置** —— 資料表、欄位、列 id、金鑰世代、格式版本，
  每一項都帶長度前綴 —— 作為 AEAD 的關聯資料。沒有這一層，有檔案寫入權限的人
  可以把一個帳號的加密金鑰複製到另一個帳號那列，而 neko-auth 會照常顯示 A 的
  驗證碼卻標著 B 的名稱。顯示驗證碼正是這個程式的全部工作，所以金鑰被調包是
  可以直接利用的。
- **KDF 參數被金鑰包裝本身驗證。** 把它們改小讓破解變便宜，不會削弱保險庫，
  只會讓它打不開。
- **一個涵蓋全部列集合和單調遞增序號的保險庫層級 HMAC**，能抓到被刪除的列、
  被插入的列，以及「舊檔案拼上新列」。逐列繫結看不到這些中的任何一個，因為
  每一列單獨看都是有效的。

### 明文存了什麼

兩個欄位：一個隨機的列 id 和一個世代計數器。再加上不可避免的列數。

時間戳記放在加密區塊裡而不是欄位裡，因為明文的 `created_at`/`updated_at`
是一份行為側寫 —— 你什麼時候設定每個雙重驗證、最近碰過哪個。排序在記憶體裡做；
一個保序的欄位會洩露你那些發行方名稱的字母順序。

### 行程衛生

啟動時，在任何敏感資料進入記憶體之前：停用 core dump、把 `umask` 設成 `0077`
（SQLite 用行程 umask 而不是資料庫的 mode 來建立 `-wal` 和 `-shm` 檔案），
以及安裝一個只顯示固定文字的 panic hook，而不是顯示可能含有已解密內容的酬載。

發布設定刻意**不設** `panic = "abort"`。它聽起來更安全，但在這裡方向是反的：
abort 跳過堆疊展開，跳過 `Drop`，也就跳過了所有記憶體抹除。

## 儲存位置

| | |
|---|---|
| Linux | `$XDG_DATA_HOME/neko-auth/`（預設 `~/.local/share/neko-auth/`） |
| macOS | `~/Library/Application Support/neko-auth/` |
| Windows | `%LOCALAPPDATA%\neko-auth\` |

Windows 上用 `%LOCALAPPDATA%` 而不是 `%APPDATA%` 是刻意的：漫遊設定檔會在
登入時被複製到網域伺服器，保險庫預設不該在網路上跑來跑去。

可以用 `--vault <路徑>` 或 `NEKO_AUTH_VAULT` 覆寫；`NEKO_AUTH_HOME` 則移動
整個目錄。

在 Unix 上，保險庫、它的附屬檔案和所有匯出都是 `0600`，而一個群組或全域可讀的
保險庫會在啟動時產生警告 —— 這正是「從一個做壞了的 tar 檔還原」被發現的方式。
Windows 上沒有 mode 位元；`%LOCALAPPDATA%` 的預設 ACL 已經把存取限制在你、
SYSTEM 和系統管理員，而手寫 DACL 程式碼只會增加風險，並不能擋住本機管理員。

**不要把保險庫放進 Dropbox、iCloud 雲碟或 OneDrive。** 一個使用中的 SQLite
檔案加上同步用戶端就是一台損壞製造機。neko-auth 在預寫日誌無法啟用時會警告，
那通常就是徵兆。把保險庫放在本機磁碟，用 `export encrypted` 做備份。

## 更新

```bash
neko-auth update --check
neko-auth update
```

這是唯一會碰網路的指令。沒有啟動檢查，也沒有遙測：一個賣點是「留在你電腦上」
的工具，不該悄悄告訴伺服器你用得有多頻繁。

下載會被驗證兩次：先用編譯進執行檔的公鑰驗證校驗和檔案的 Ed25519 簽章，
再用那個檔案裡的 SHA-256 驗證封存檔。單靠校驗和只能證明位元組從提供它的人
那裡完整送達；簽章才是 GitHub 帳號被入侵時依然成立的那道檢查。沒有編入簽章
公鑰的組建會回報新版本，但拒絕安裝。

用 `config update_repo <owner>/<repo>` 設定來源倉庫，或在建置時用
`NEKO_AUTH_REPO` 指定。

## 從損壞中還原

```bash
neko-auth doctor
```

它會執行 SQLite 的完整性檢查、驗證保險庫簽章，然後嘗試解密每一個帳號，
**把失敗的那些點名回報出來，而其餘帳號照常運作**。最後這一點正是逐欄位加密
（而不是整檔加密）在實務上的回報：整檔加密時，一個壞的分頁落在錯誤的位置
就可能讓整個保險庫打不開。

## 開發

```bash
cargo test                       # 單元測試和整合測試
cargo test --no-default-features # 最小組建
cargo clippy --all-targets
```

TOTP 實作直接對照 RFC 4226 和 RFC 6238 的官方測試向量驗證，包括 SHA-256 和
SHA-512 兩組 —— 它們用的種子長度不同，把 20 位元組的 SHA-1 種子套給三者是這裡
的標準錯誤，產出的向量看著像樣其實是錯的。

安全相關的論斷都有直接陳述它們的測試：翻轉密文的任何一個位元組都會被拒絕；
把金鑰搬到另一個帳號的列上不會解密；把金鑰搬進一個會被顯示的欄位裡不會解密；
削弱儲存的 KDF 參數會讓金鑰包裝失效；刪掉一列會被保險庫簽章抓到；工具寫出的
每個檔案都是 `0600`；以及把信箱和密碼重新切分不會衍生出同一把金鑰。

翻譯也有測試：參數在每種語言裡都要正確代入、計數短語在英文裡變化而在其他語言
裡不變、繁體條目使用台灣而非大陸用語，以及中日文句子裡數字與文字之間的空格。
