# neko-auth

---

两步验证码从不离开你的机器。一个命令行验证器，数据存在本地加密保险库里，
用一个邮箱加一个密码解锁 —— 而这两样东西哪里都没有保存。

## 这东西是干什么的

两步验证的密钥存进本地一个加密的 SQLite 保险库。不同步、不上传，也没有账号
要登录。全程唯一会打开网络连接的命令是 `update`，而且只在你主动运行时。

```
$ neko-auth
邮箱：zoe@example.com
主密码：

neko-auth 0.1.0
保险库：~/.local/share/neko-auth/vault.db
闲置 300 秒后自动锁定
输入 `help` 查看命令，`exit` 退出

neko-auth › get github
GitHub (zoe@example.com)
  123 456   █████████░░░ 22 秒
```

## 威胁模型

这一节是整个 README 最重要的部分。在把任何东西交给它之前，请先读完。

**neko-auth 保护什么。** 保护**静态的**保险库：笔记本被偷、备份被拷走、`.db`
文件被人从硬盘上捞走 —— 也就是 neko-auth 没在运行的时候。这就是威胁模型，
而且这就是全部的威胁模型。

拿到你保险库文件的攻击者，能知道的只有**里面有几个账号**。发行方、账号名、
密钥、算法、位数、周期、时间戳全部是密文，而且密文做了填充，长度也不会把名字
泄露出去。猜一次凭据的成本是一次完整的 Argon2id 运算 —— 库里没有任何更便宜的
校验点。

保险库要用**一个邮箱和一个密码一起**解锁，而**两者都不在文件里**。不存邮箱，
也不存邮箱的哈希。拷走保险库的人必须把两半都猜对，而文件不会告诉他任何一半的
线索。代价在下面写清楚了：邮箱打错和密码输错是同一个报错，而忘了当初用的是哪个
邮箱，和忘记密码一样，保险库就永久打不开了。

**neko-auth 不保护什么。**

- **恶意软件，或任何以你的身份运行的进程。** 它可以直接读这个进程的内存
  （`ptrace`、`task_for_pid`、`ReadProcessMemory`）。任何用户态程序都拦不住。
- **root 或内核级的攻击者。** 同理，而且更甚。
- **被换出到 swap 的密钥。** 我们不做 `mlock`：Linux 上 `RLIMIT_MEMLOCK`
  常常只有 64 KiB，`VirtualLock` 受工作集配额限制，而且两者都撑不过休眠。
  锁一个你锁不住的内存页，是虚假承诺而不是防护。**请使用全盘加密** ——
  FileVault、LUKS、BitLocker —— 并给 swap 也加密。
- **系统崩溃转储。** 我们在启动时禁用了 core dump，但 macOS 的 ReportCrash、
  Windows 错误报告和 systemd-coredump 不在我们控制范围内。
- **有人把你的保险库回滚到一个真正完整的旧副本。** 库级签名能抓到被删除的行、
  被插入的行，以及"旧文件拼上新行"，但要检测整体回滚需要文件之外的状态，
  这个工具没有。
- **你的剪贴板。** `get -c` 会把验证码放到一个所有以你身份运行的进程都能读的
  地方，操作系统还可能把它同步到你的其他设备上。15 秒后会清空，但那是缓解，
  不是防护。*（macOS 的 `org.nspasteboard.ConcealedType` 和 Windows 的
  `ExcludeClipboardContentFromMonitorProcessing` 这两个隐私提示位**目前没有
  设置**；要设它们得绕开跨平台剪贴板库直接调原生 API，会和它自己的开关剪贴板
  操作产生竞态。）*

**内存擦除是尽力而为。** 密钥材料放在会自我擦除的缓冲区里，用的是 volatile
写入加编译器屏障 —— 这是 stable Rust 上能拿到的最强保证。但它擦不掉寄存器溢出
和优化器已经产生的中间副本。

**没有任何找回机制。** 邮箱和密码任何一个忘了，那个保险库里的账号就永久没了。
请做加密备份。

## 安装

```bash
cargo install --path .
```

或者只编译一个二进制：

```bash
cargo build --release
```

保险库是一个静态二进制，没有运行时依赖；SQLite 是编译进去的。

如果不想要二维码图片解码（它会引入 `image`，一大片解析代码面）和自更新：

```bash
cargo build --release --no-default-features
```

## 上手

```bash
neko-auth init            # 创建保险库，设置邮箱和主密码
neko-auth                 # 进入交互式会话
```

### 从谷歌验证器搬过来

1. 在 App 里：**⋮ → 转移账号 → 导出账号**，选好账号，让它显示二维码。
2. 每张二维码都截图。**账号多的时候会分成好几张** —— 全都要截。
3. 一次性全部导入：

```bash
neko-auth import qr part1.png part2.png part3.png
```

部分导入会被拒绝。给它三张里的两张，它会明说还差哪张、并且什么都不存，
而不是让你以为已经迁移完成、其实大部分账号还只在手机上。

4. **在删掉手机上的任何东西之前，先核对。** 把几个验证码并排比一遍：

```bash
neko-auth watch
```

只有在验证码完全一致之后，才考虑移除手机上的 App —— 而且即便到那时，
在第二台设备上留一份，通常也比只有一份更明智。

### 其他导入方式

```bash
neko-auth import uri            # 在不回显的提示下粘贴 otpauth:// 链接
neko-auth import file list.txt  # 一个装着 otpauth:// 或迁移链接的文件
neko-auth add                   # 手动输入网站"无法扫码？"给的那串 Base32 密钥
```

密钥永远不接受作为命令行参数。`argv` 通过 `ps` 对本机所有进程可见，
而且非交互调用还会把它留在 shell 历史里。

导出用的二维码很密集 —— version 20 起步 —— 而解码器的二值化对每个模块占几个
像素很敏感，所以一张手机能秒读的截图，在原始分辨率下可能解不出来。因此每张图
都会先按几种缩放比例重试再放弃。如果还是读不出来，把截图裁到只剩二维码再试。

## 命令

下面每一条在会话里和作为一次性命令都能用。

| | |
|---|---|
| `ls [模式]` | 列出账号及其当前验证码 |
| `get <名字> [-c]` | 打印某个验证码；`-c` 同时复制到剪贴板 |
| `watch [模式]` | 全屏实时看板，带倒计时 |
| `add` | 在不回显的提示下添加账号 |
| `import uri｜qr｜file` | 从链接、二维码图片或文件导入 |
| `rm <名字>` | 删除账号，需确认 |
| `rename <名字>` | 修改账号的发行方或标签 |
| `show <名字>` | 查看某个账号的参数，不含密钥 |
| `reveal <名字>` | 打印账号的密钥；需要手动输入 `REVEAL` |
| `export encrypted <路径>` | 写出加密的 `.nekobak` 备份 |
| `export plain <路径>` | 写出明文 `otpauth://` 链接；需要手动输入 `YES` |
| `restore <路径>` | 从加密备份导入 |
| `passwd` | 修改邮箱与主密码 |
| `doctor` | 检查保险库是否损坏 |
| `config [键] [值]` | 查看或修改设置 |
| `lang [代码]` | 查看或切换界面语言 |
| `lock` | 立即从内存中擦除密钥 |
| `update [--check]` | 检查新版本（唯一会联网的命令） |

每条命令都接受前导 `/`，所以 `/help` 和 `help` 一样能用。

会话里 Tab 可以补全命令和账号名，历史**只保存在内存中**。`show coinbase`
本身就是敏感元数据 —— 它说明了你在哪些服务上有账号 —— 没有理由活过本次会话。

### 备份

```bash
neko-auth export encrypted ~/vault.nekobak
```

`.nekobak` 是一个自包含、带版本号的加密归档，刻意不是 SQLite 文件的副本：
备份应该活得比产生它的 schema 更久，最好也比这个程序更久。它的字节布局写在
[`src/export.rs`](src/export.rs) 开头，详细到足够用大约五十行代码重新实现。

`export plain` 把你的密钥写成普通的 `otpauth://` 链接。它存在，是因为那是
**你的**密钥、你必须能带走 —— 但它会要求你手动输入 `YES`，文件权限 `0600`，
并提醒你用完立刻删除。

### 离开

`export plain` 产出的链接任何其他验证器都能接受。这里没有锁定。

## 关于邮箱

保险库的密钥由邮箱**和**密码共同派生，而不是只由密码派生：

```
Argon2id( "neko-auth/identity/v1" ‖ len(邮箱) ‖ 邮箱 ‖ len(密码) ‖ 密码 , salt )
```

每一段都带长度前缀。直接拼接会产生要命的歧义：`("a@b.com", "xyz")` 和
`("a@b.co", "mxyz")` 连起来是同一个字符串，那样其中一组凭据就能打开用另一组
创建的保险库。

邮箱**不保存在任何地方** —— 这正是它的全部意义。保存它，哪怕只保存哈希，
都等于把一半的秘密交给拷走文件的人，而且那样它就不比库里已有的 32 字节随机盐
更有用。

**邮箱在输入时会回显，密码不会。** 这个不对称是刻意的。保护保险库的是邮箱
**不在文件里**，这一点跟它是否出现在屏幕上无关。隐藏它只能防肩窥 —— 不在上面
那个威胁模型里 —— 却要付出实实在在的代价：两半都看不见的时候，邮箱打错既无法
在打错的当下察觉，之后也永远和密码错误无法区分。`neko-auth init` 完成后还会
把归一化后的邮箱回显一次，因为那是你唯一能看到保险库究竟期待什么的时刻。

如果你更想让它隐藏，`config hide_email true` 可以恢复，那时设置阶段会改成
问两遍，而不是靠你用眼睛核对。

在决定用它之前，值得知道的几件事：

- 邮箱错和密码错给出同一个报错。这不是故弄玄虚：认证标签确实无法分辨是哪一半
  错了。
- 邮箱在使用前会去掉首尾空白并转小写，所以 `Zoe@Example.com` 和
  `zoe@example.com` 是同一个。RFC 5321 确实规定本地部分大小写敏感；但没有任何
  邮件服务商真的这么做，而一个打不开的保险库是远比理论上的不一致更糟的结果。
- **把你用的是哪个邮箱写下来**，和备份放在一起。它是秘密，所以请放在你放密码的
  地方 —— 但它比你特意想出来的密码更容易记岔。

`.nekobak` 备份默认有自己独立的一个密码，因为它是一个独立的文件。
`export encrypted --same-password` 会改用你解锁时那组邮箱和密码来加密它。

## 语言

neko-auth 支持 English、简体中文、繁體中文 和 日本語。默认跟随你的系统区域设置，
所以在一台设成日语的机器上，它开箱就是日语。

```bash
neko-auth --lang zh-Hant          # 只影响这一次
neko-auth config language ja      # 记住
```

或者在会话里：

```
neko-auth › lang
neko-auth › lang zh-Hans
```

可用的值是 `auto`（跟随 `$LC_ALL`、`$LC_MESSAGES` 或 `$LANG`）、`en`、
`zh-Hans`、`zh-Hant` 和 `ja`。POSIX 区域名也能用，所以
`--lang zh_TW.UTF-8` 会按你预期的那样工作。

繁体中文用的是台湾用语（檔案、設定、網路、金鑰），而不是从简体逐字转换 ——
后者正是这类本地化最常见的出错方式。

有两处刻意保留英文：

- 确认危险操作时要输入的词 —— `YES` 和 `REVEAL`。它们是固定令牌；翻译只会
  多出一种打错不可逆操作的方式。
- clap 自己的参数解析错误（"unexpected argument" 之类）。neko-auth 输出的一切
  都翻译了，包括 `--help`，但库内部的字符串够不着。

新增一种语言，就是在 [`src/i18n/messages.rs`](src/i18n/messages.rs) 的每一条
下面加一行。宏要求每条消息都有全部语言，所以漏翻是编译错误，而不是某条悄悄
退回英文。

## 它是怎么工作的

### 密钥层级

```
邮箱 + 密码 ─Argon2id(salt, m/t/p)──▶ KEK
                                       │
                                       └─ 解开 ─▶ DEK（随机生成，密文存库）
                                                     │
                                   ┌─────────────────┴─────────────────┐
                                 字段密钥                            元数据密钥
                              逐字段加解密                        库级完整性签名
```

两层的存在是为了正确性，不是速度。修改凭据只需在一个事务里重新包装 32 字节，
这是原子的。重新加密整个保险库不是原子的，而一次做到一半的修改就是一次数据
丢失事件。

**验证就是解开 DEK，此外什么都没有。** 凭据错了就得到错的 KEK，AEAD 标签校验
失败。库里刻意不存密码哈希，也不存邮箱哈希：前者是这类工具的经典错误 ——
一个比它要保护的 Argon2id 便宜十亿倍的校验点 —— 后者则会把一个原本磁盘上根本
没有的秘密送出去一半。

同样刻意**不做错误次数计数、不做自毁**。攻击者是拷走文件离线爆破的，我们的
计数器在那边根本不运行。这种功能唯一能做到的，就是给你一个亲手毁掉自己二次
验证的方式。

### 加密

- **Argon2id**，默认 256 MiB / 3 轮 / 4 通道（`--kdf-profile interactive`
  是 64 MiB，`paranoid` 是 1 GiB）。参数存在库里，因为它们是哈希函数的一部分 ——
  在一台机器上创建的保险库必须能在另一台上打开。读回时会做上下界检查：
  `argon2` 自己不做上界检查，所以否则的话，把存储的 `m_cost` 改一个字节
  就是一次内存耗尽崩溃。
- **XChaCha20-Poly1305** 用于每个字段。192 位的 nonce 是随机 nonce 无条件安全
  的原因。AES-GCM 的 96 位 nonce 会把你推向计数器，而计数器在一个可以从备份
  恢复的数据库里是个陷阱：恢复上个月的副本、再加两个账号，你就重用了一个。
  GCM 的 nonce 重用会泄露认证密钥本身。
- **每个密文都绑定到它所在的位置** —— 表、列、行 id、密钥代数、格式版本，
  每一项都带长度前缀 —— 作为 AEAD 的关联数据。没有这一层，有文件写权限的人
  可以把一个账号的加密密钥复制到另一个账号那行，而 neko-auth 会照常打印 A 的
  验证码却标着 B 的名字。显示验证码正是这个程序的全部工作，所以密钥被调包是
  可以直接利用的。
- **KDF 参数被密钥包装本身认证。** 把它们改小让爆破变便宜，不会削弱保险库，
  只会让它打不开。
- **一个覆盖全部行集合和单调递增序号的库级 HMAC**，能抓到被删除的行、被插入的
  行，以及"旧文件拼上新行"。逐行绑定看不到这些中的任何一个，因为每一行单独看
  都是有效的。

### 明文存了什么

两列：一个随机的行 id 和一个代数计数器。再加上不可避免的行数。

时间戳放在加密块里而不是列里，因为明文的 `created_at`/`updated_at` 是一份行为
画像 —— 你什么时候配的每个二次验证、最近碰过哪个。排序在内存里做；一个保序的
列会泄露你那些发行方名字的字母顺序。

### 进程卫生

启动时，在任何敏感数据进入内存之前：禁用 core dump、把 `umask` 设成 `0077`
（SQLite 用进程 umask 而不是数据库的 mode 来创建 `-wal` 和 `-shm` 文件），
以及安装一个只打印固定文案的 panic hook，而不是打印可能含有已解密内容的载荷。

发布配置刻意**不设** `panic = "abort"`。它听起来更安全，但在这里方向是反的：
abort 跳过栈展开，跳过 `Drop`，也就跳过了所有内存擦除。

## 存储位置

| | |
|---|---|
| Linux | `$XDG_DATA_HOME/neko-auth/`（默认 `~/.local/share/neko-auth/`） |
| macOS | `~/Library/Application Support/neko-auth/` |
| Windows | `%LOCALAPPDATA%\neko-auth\` |

Windows 上用 `%LOCALAPPDATA%` 而不是 `%APPDATA%` 是刻意的：漫游配置文件会在
登录时被复制到域服务器，保险库默认不该在网络上跑来跑去。

可以用 `--vault <路径>` 或 `NEKO_AUTH_VAULT` 覆盖；`NEKO_AUTH_HOME` 则移动
整个目录。

在 Unix 上，保险库、它的 sidecar 文件和所有导出都是 `0600`，而一个组内或全局
可读的保险库会在启动时产生警告 —— 这正是"从一个做坏了的 tar 包恢复"被发现的
方式。Windows 上没有 mode 位；`%LOCALAPPDATA%` 的默认 ACL 已经把访问限制在你、
SYSTEM 和管理员，而手写 DACL 代码只会增加风险，并不能挡住本机管理员。

**不要把保险库放进 Dropbox、iCloud Drive 或 OneDrive。** 一个活的 SQLite 文件
加上同步客户端就是一台损坏制造机。neko-auth 在预写日志无法启用时会警告，
那通常就是症状。把保险库放在本地磁盘，用 `export encrypted` 做备份。

## 更新

```bash
neko-auth update --check
neko-auth update
```

这是唯一会碰网络的命令。没有启动检查，也没有遥测：一个卖点是"留在你机器上"的
工具，不该悄悄告诉服务器你用得有多频繁。

下载会被验证两次：先用编译进二进制的公钥验证校验和文件的 Ed25519 签名，
再用那个文件里的 SHA-256 校验归档。单靠校验和只能证明字节从提供它的人那里
完整到达；签名才是 GitHub 账号被攻破时依然成立的那道检查。没有编入签名公钥的
构建会报告新版本，但拒绝安装。

用 `config update_repo <owner>/<repo>` 配置来源仓库，或在构建时用
`NEKO_AUTH_REPO` 指定。

---

## 从损坏中恢复

```bash
neko-auth doctor
```

它会跑 SQLite 的完整性检查、验证库级签名，然后尝试解密每一个账号，
**把失败的那些点名报出来，而其余账号照常工作**。最后这一点正是逐字段加密
（而不是整文件加密）在实践中的回报：整文件加密时，一个坏页落在错误的位置
就可能让整个保险库打不开。

## 开发

```bash
cargo test                       # 单元测试和集成测试
cargo test --no-default-features # 最小构建
cargo clippy --all-targets
```

TOTP 实现直接对照 RFC 4226 和 RFC 6238 的官方测试向量校验，包括 SHA-256 和
SHA-512 两组 —— 它们用的种子长度不同，把 20 字节的 SHA-1 种子套给三者是这里的
标准错误，产出的向量看着像样其实是错的。

安全相关的论断都有直接陈述它们的测试：翻转密文的任何一个字节都会被拒绝；
把密钥搬到另一个账号的行上不会解密；把密钥搬进一个会被显示的列里不会解密；
削弱存储的 KDF 参数会让密钥包装失效；删掉一行会被库级签名抓到；工具写出的每个
文件都是 `0600`；以及把邮箱和密码重新切分不会派生出同一把密钥。

翻译也有测试：参数在每种语言里都要正确插值、计数短语在英语里变位而在其他语言里
不变、繁体条目使用台湾而非大陆用语，以及中日文句子里数字与文字之间的空格。
