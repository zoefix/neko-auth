# Neko Auth

---

二要素認証のコードが、このマシンから出ることはありません。暗号化されたローカル
保管庫を持つコマンドラインの認証ツール。どこにも保存されていないメールアドレスと
パスワードの組み合わせで解錠します。

## これは何のためのものか

二要素認証のシークレットを、ローカルの暗号化された SQLite 保管庫に保存します。
同期もアップロードもせず、サインインするアカウントもありません。ネットワークに
接続する唯一のコマンドは `update` で、しかも実行したときだけです。

```
$ neko-auth
メールアドレス: zoe@example.com
マスターパスワード:

neko-auth 0.1.0
保管庫: ~/.local/share/neko-auth/vault.db
300 秒操作がないと自動でロックします
`help` でコマンド一覧、`exit` で終了

neko-auth › get github
GitHub (zoe@example.com)
  123 456   █████████░░░ 22 秒
```

## 脅威モデル

この節が README でもっとも重要な部分です。何かを預ける前に、必ず読んでください。

**neko-auth が守るもの。** 保管庫の**保存状態**です。ノート PC の盗難、
バックアップの持ち出し、ディスクから抜き取られた `.db` ファイル —— つまり
neko-auth が動いていないときの話です。それが脅威モデルであり、それがすべてです。

保管庫ファイルを手に入れた攻撃者にわかるのは、**アカウントが何件あるか**だけ
です。発行元、アカウント名、シークレット、アルゴリズム、桁数、周期、日時は
すべて暗号化され、暗号文はパディングされているので長さから名前が推測される
こともありません。資格情報を 1 回推測するコストは Argon2id の完全な 1 回分で、
ファイルの中にそれより安く済む確認手段は存在しません。

保管庫は**メールアドレスとパスワードの組み合わせ**で解錠し、**どちらもファイル
には保存されていません**。アドレスも、そのハッシュもです。保管庫をコピーした
攻撃者は両方を当てる必要があり、ファイルはそのどちらについても何も語りません。
その裏返しは以下にはっきり書いてあります。アドレスの打ち間違いはパスワード誤り
と区別がつかず、どのアドレスを使ったか忘れれば、パスワードを忘れたときと同じく
保管庫は永久に開きません。

**neko-auth が守らないもの。**

- **マルウェア、および同じユーザーで動く他のプロセス。** それらはこのプロセスの
  メモリを直接読めます（`ptrace`、`task_for_pid`、`ReadProcessMemory`）。
  ユーザー空間のプログラムに防ぎようはありません。
- **root やカーネルレベルの攻撃者。** 同じ理由で、さらに徹底的にです。
- **スワップに書き出されたシークレット。** `mlock` は使いません。Linux の
  `RLIMIT_MEMLOCK` は 64 KiB のことが多く、`VirtualLock` はワーキングセットの
  上限に縛られ、どちらもハイバネーションには耐えません。確実にロックできない
  ページをロックするのは、防御ではなく空約束です。**フルディスク暗号化を
  使ってください** —— FileVault、LUKS、BitLocker —— そしてスワップも暗号化を。
- **システムのクラッシュレポーター。** 起動時に core dump は無効化しますが、
  macOS の ReportCrash、Windows エラー報告、systemd-coredump は制御の外です。
- **保管庫を、本当に整合した古いコピーへ巻き戻す操作。** 保管庫全体の署名は
  削除された行、挿入された行、古いファイルに新しい行を継ぎ足したものを検出
  しますが、まるごとの巻き戻しを検出するにはファイルの外に状態が要り、この
  ツールはそれを持ちません。
- **クリップボード。** `get -c` はコードを、同じユーザーで動くあらゆるプロセス
  が読める場所に置きます。OS が他の端末へ同期することもあります。15 秒後に
  消去しますが、それは緩和であって防御ではありません。*(macOS の
  `org.nspasteboard.ConcealedType` と Windows の
  `ExcludeClipboardContentFromMonitorProcessing` というプライバシー用のヒントは
  **現在は設定していません**。設定するにはクロスプラットフォームの
  クリップボードライブラリを迂回してネイティブ API を直接叩く必要があり、
  そのライブラリ自身の開閉処理と競合するためです。)*

**メモリの消去はベストエフォートです。** 鍵素材は自分で自分を消去する
バッファに置かれ、volatile 書き込みとコンパイラフェンスを使っています ——
stable Rust で得られる最強の保証です。それでもレジスタへの退避や、最適化器が
すでに作った中間コピーまでは消せません。

**復旧手段はありません。** メールアドレスかパスワードのどちらかを忘れれば、
その保管庫のアカウントは永久に失われます。暗号化バックアップを作ってください。

## インストール

**macOS・Linux・WSL:**

```bash
curl -fsSL https://raw.githubusercontent.com/zoefix/neko-auth/main/install.sh | sh
```

**Windows PowerShell:**

```powershell
irm https://raw.githubusercontent.com/zoefix/neko-auth/main/install.ps1 | iex
```

**Windows CMD:**

```
curl -fsSL https://raw.githubusercontent.com/zoefix/neko-auth/main/install.cmd -o install.cmd && install.cmd
```

インストーラーはこのマシン向けのリリースビルドをダウンロードし、公開されて
いるチェックサムと照合し、PATH に追加して終了します。保管庫は作らず、何も
尋ねません。新しいターミナルを開いて:

```bash
neko-auth init
```

スクリプトをシェルにパイプするのは、その URL が返すものを何であれ実行すると
いうことなので、先に読みたければそのほうが妥当です ——
[install.sh](install.sh) はおよそ百行です。`NEKO_AUTH_INSTALL_DIR` で配置先を
変えられ、`NEKO_AUTH_NO_PATH=1` を付けるとシェルの起動ファイルに触れません。

### ソースからビルドする

```bash
cargo install --git https://github.com/zoefix/neko-auth
```

できあがるのは実行時依存のない単一の静的バイナリで、SQLite は組み込まれます。
QR 画像のデコード（`image` という大きな解析コードを引き込みます）と自動更新を
外す場合:

```bash
cargo build --release --no-default-features
```

## はじめかた

```bash
neko-auth init            # 保管庫を作り、メールアドレスとマスターパスワードを設定
neko-auth                 # 対話セッションを開く
```

### Google 認証システムから移す

1. アプリで **⋮ → アカウントの移行 → アカウントをエクスポート** を選び、
   アカウントを選択して QR コードを表示させます。
2. 表示された QR コードをすべてスクリーンショットで保存します。
   **アカウントが多いと複数枚に分かれます** —— 全部撮ってください。
3. まとめて取り込みます:

```bash
neko-auth import qr part1.png part2.png part3.png
```

一部だけの取り込みは拒否されます。3 枚中 2 枚を渡すと、どれが足りないかを
はっきり伝えたうえで何も保存しません。移行が終わったつもりで、実際には大半の
アカウントが電話にしか無い、という状態を避けるためです。

4. **電話から何かを消す前に、必ず確認してください。** いくつかのコードを
   並べて見比べます:

```bash
neko-auth watch
```

コードが一致してはじめて、電話のアプリを消すことを検討してください ——
それでも、二台目の端末に控えを残しておくほうが、控えが一つだけよりたいてい
賢明です。

### ほかの取り込み方

```bash
neko-auth import uri            # 非表示のプロンプトに otpauth:// URI を貼る
neko-auth import file list.txt  # otpauth:// や移行 URI を並べたファイル
neko-auth add                   # 「スキャンできない場合」の Base32 を手入力
```

シークレットをコマンドライン引数として受け取ることは決してありません。`argv` は
`ps` から同じマシンのあらゆるプロセスに見えますし、非対話的な実行ではシェルの
履歴にも残ります。

エクスポート用の QR コードは非常に密度が高く（バージョン 20 以上）、デコーダーの
二値化は 1 モジュールが何ピクセルを占めるかに敏感です。そのため、電話なら
一瞬で読めるスクリーンショットが元の解像度では読めないことがあります。各画像は
あきらめる前に複数の倍率で読み直します。それでも読めない場合は、コードだけが
残るように切り抜いてから試してください。

## コマンド

以下はすべて、セッション内でも単発のコマンドとしても使えます。

| | |
|---|---|
| `ls [パターン]` | アカウントと現在のコードを一覧表示 |
| `get <名前> [-c]` | コードを 1 つ表示。`-c` でクリップボードにもコピー |
| `watch [パターン]` | カウントダウン付きの全画面ライブ表示 |
| `add` | 非表示のプロンプトでアカウントを追加 |
| `import uri｜qr｜file` | URI・QR 画像・ファイルから取り込む |
| `rm <名前>` | アカウントを削除（確認あり） |
| `rename <名前>` | 発行元やラベルを変更 |
| `show <名前>` | アカウントの設定を表示（シークレットは除く） |
| `reveal <名前>` | シークレットを表示。`REVEAL` の入力が必要 |
| `export encrypted <パス>` | 暗号化された `.nekobak` バックアップを書き出す |
| `export plain <パス>` | 平文の `otpauth://` を書き出す。`YES` の入力が必要 |
| `restore <パス>` | 暗号化バックアップから取り込む |
| `passwd` | メールアドレスとマスターパスワードを変更 |
| `doctor` | 保管庫の破損を確認 |
| `config [キー] [値]` | 設定の表示・変更 |
| `lang [コード]` | 表示言語の確認・切り替え |
| `lock` | 鍵を今すぐメモリから消去 |
| `update [--check]` | 新しいリリースを確認（唯一ネットワークに触れるコマンド） |

どのコマンドも先頭の `/` を受け付けるので、`/help` も `help` と同じに動きます。

セッションでは Tab でコマンド名とアカウント名が補完され、履歴は
**メモリ上にのみ**保持されます。`show coinbase` はそれ自体が機微なメタデータ
—— どのサービスにアカウントがあるかを示します —— なので、セッションより長く
残る理由がありません。

### バックアップ

```bash
neko-auth export encrypted ~/vault.nekobak
```

`.nekobak` は自己完結でバージョン付きの暗号化アーカイブであり、SQLite ファイル
の複製ではないのは意図的です。バックアップは、それを生んだスキーマより、
できればプログラムよりも長生きすべきだからです。バイト配置は
[`src/export.rs`](src/export.rs) の冒頭に、五十行ほどで再実装できる程度に
書いてあります。

`export plain` はシークレットをそのままの `otpauth://` URI として書き出します。
これがあるのは、それが**あなたの**シークレットであり、持ち出せなければならない
からです —— ただし `YES` の入力を求め、ファイルは `0600` で書き、使い終えたら
削除するよう促します。

### 出ていくとき

`export plain` が出力する URI は、ほかのどの認証アプリでも受け取れます。
囲い込みはありません。

## メールアドレスについて

保管庫の鍵は、パスワードだけでなく、メールアドレス**と**パスワードから導かれます:

```
Argon2id( "neko-auth/identity/v1" ‖ len(アドレス) ‖ アドレス ‖ len(パスワード) ‖ パスワード , salt )
```

各要素には長さが前置されています。単純に連結すると、まずい形で曖昧になります。
`("a@b.com", "xyz")` と `("a@b.co", "mxyz")` はつなげると同じ文字列になり、
一方の組で作った保管庫がもう一方の組で開いてしまいます。

アドレスは**どこにも保存されません** —— それこそがこの仕組みの要点です。
保存すること、ハッシュだけでも保存することは、ファイルをコピーした相手に
秘密の半分を渡すことであり、しかもすでにある 32 バイトのランダムなソルト以上の
意味を持ちません。

**アドレスは入力しながら表示され、パスワードは表示されません。** この非対称は
意図したものです。保管庫を守っているのはアドレスが*ファイルの中にない*ことで
あり、それは画面に映るかどうかとは無関係です。隠しても防げるのは肩越しに覗く
相手だけで —— それは上の脅威モデルの外です —— 代わりに実害があります。両方が
見えないと、アドレスの打ち間違いはその瞬間に気づけず、以後もパスワード誤りと
永遠に区別がつきません。`neko-auth init` は最後に正規化したアドレスを表示
します。保管庫が実際に何を要求するのかを確認できるのは、そこだけだからです。

隠すほうがよければ `config hide_email true` で元に戻せます。その場合は目視で
確認できないぶん、設定時に二度入力を求めます。

使うと決める前に知っておく価値のあることが、いくつかあります。

- アドレスの誤りとパスワードの誤りは同じメッセージになります。これはもったい
  ぶっているのではなく、認証タグにはどちらが誤りか本当に判別できません。
- アドレスは前後の空白を落とし、小文字に揃えてから使います。したがって
  `Zoe@Example.com` と `zoe@example.com` は同じです。RFC 5321 はローカル部を
  大文字小文字の区別ありと定めていますが、そう扱うメールプロバイダーは現実に
  存在せず、開かない保管庫のほうが理論上の不一致よりはるかに悪い結果です。
- **どのアドレスを使ったか書き留めて**、バックアップと一緒に保管してください。
  それは秘密なのでパスワードと同じ場所に置くべきですが、自分で選んだパスワード
  よりも思い違いをしやすい秘密です。

`.nekobak` バックアップは独立したファイルなので、既定では独自のパスワードを
持ちます。`export encrypted --same-password` を使うと、解錠に使うのと同じ
アドレスとパスワードの組で暗号化します。

## 言語

neko-auth は English、简体中文、繁體中文、日本語 に対応しています。既定では
ロケールに従うので、日本語に設定されたマシンでは何もしなくても日本語で起動
します。

```bash
neko-auth --lang zh-Hant          # この実行だけ
neko-auth config language ja      # 記憶する
```

セッション内からも切り替えられます:

```
neko-auth › lang
neko-auth › lang ja
```

指定できる値は `auto`（`$LC_ALL`、`$LC_MESSAGES`、`$LANG` に従う）、`en`、
`zh-Hans`、`zh-Hant`、`ja` です。POSIX のロケール名も使えるので、
`--lang zh_TW.UTF-8` は期待どおりに動きます。

繁体字中国語は簡体字からの一文字ずつの変換ではなく、台湾の語彙（檔案、設定、
網路、金鑰）で書かれています。前者はこの種のローカライズが読み手にとって
不自然になる、いちばんよくある原因です。

英語のまま残している箇所が二つあります。

- 取り返しのつかない操作を確認するために入力する語 —— `YES` と `REVEAL`。
  これらは固定のトークンであり、翻訳しても打ち間違えの経路が増えるだけです。
- clap 自身の引数解析エラー（"unexpected argument" など）。`--help` を含め
  neko-auth が出力するものはすべて翻訳していますが、ライブラリ内部の文字列には
  手が届きません。

言語を増やす作業は、[`src/i18n/messages.rs`](src/i18n/messages.rs) の各項目に
一行ずつ足すことです。マクロがすべてのメッセージにすべての言語を要求するので、
訳し漏れは黙って英語に落ちるのではなくコンパイルエラーになります。

## しくみ

### 鍵の階層

```
アドレス + パスワード ─Argon2id(salt, m/t/p)──▶ KEK
                                                 │
                                                 └─ 解く ─▶ DEK（ランダム生成・暗号化して保存）
                                                               │
                                         ┌─────────────────────┴─────────────────────┐
                                     フィールド鍵                                メタデータ鍵
                                   項目ごとの暗号化                          保管庫全体の完全性 MAC
```

二層になっているのは速度ではなく正しさのためです。資格情報の変更は一つの
トランザクションで 32 バイトを包み直すだけで、これは不可分に完了します。
保管庫全体の再暗号化はそうではなく、途中で終わった変更はそのままデータ消失に
なります。

**検証は DEK を解くことそのものであり、それ以外はありません。** 資格情報が
違えば KEK が違い、AEAD のタグ検証が失敗します。パスワードのハッシュも、
アドレスのハッシュも、意図的に保存していません。前者はこの種のツールの典型的な
誤りで、守るはずの Argon2id より十億倍安い確認手段を与えてしまいます。後者は、
本来ディスク上のどこにもない秘密の半分を渡すことになります。

**失敗回数のカウントも、自動消去も、同じく意図的に実装していません。**
攻撃者はファイルをコピーしてオフラインで作業するので、こちらのカウンターは
そこでは動きません。そうした機能にできるのは、あなたが自分の二要素認証を
自分の手で壊す方法を用意することだけです。

### 暗号

- **Argon2id**、既定で 256 MiB / 3 パス / 4 レーン（`--kdf-profile interactive`
  で 64 MiB、`paranoid` で 1 GiB）。パラメーターはハッシュ関数の一部なので
  保管庫に保存されます —— あるマシンで作った保管庫は別のマシンでも開けなければ
  なりません。読み戻す際には範囲を検査します。`argon2` 自身は上限を検査しない
  ため、そうしなければ保存された `m_cost` の 1 バイト書き換えがメモリ枯渇に
  よる異常終了になります。
- 各フィールドには **XChaCha20-Poly1305**。192 ビットの nonce があるからこそ、
  ランダムな nonce が無条件に安全です。AES-GCM の 96 ビット nonce はカウンター
  の使用へ誘導しますが、バックアップから復元できるデータベースでカウンターを
  持つのは罠です。先月の複製を戻して二つアカウントを足せば、もう再利用して
  います。GCM の nonce 再利用は認証鍵そのものを漏らします。
- **すべての暗号文は、それが置かれた場所に束縛されています** —— テーブル、
  カラム、行 ID、鍵の世代、フォーマット版を、それぞれ長さ付きで AEAD の
  関連データにします。これがなければ、ファイルへの書き込み権限がある者が
  あるアカウントの暗号化済みシークレットを別の行へコピーでき、neko-auth は
  A のコードを B の名前で表示してしまいます。コードを表示することがこの
  プログラムの仕事そのものなので、すり替えられたシークレットはそのまま悪用
  できます。
- **KDF パラメーターは鍵のラップ自身によって認証されます。** 解読を安くしよう
  として値を下げても保管庫は弱くならず、単に開かなくなります。
- **行の集合と単調増加するシリアルを覆う保管庫全体の HMAC** が、削除された行、
  挿入された行、古いファイルに新しい行を継ぎ足したものを検出します。行ごとの
  束縛はそのどれも見えません。残った行はどれも単体では正当だからです。

### 平文のまま置かれているもの

二つのカラム、ランダムな行 ID と世代カウンターだけです。加えて、避けようのない
行数。

日時はカラムではなく暗号化されたブロックの中にあります。平文の
`created_at`/`updated_at` は行動の記録 —— 各二要素認証をいつ設定し、どれを
最近触ったか —— になるからです。並べ替えはメモリ上で行います。順序を保つ
カラムは、発行元名のアルファベット順を漏らします。

### プロセスの衛生

起動直後、機微なものがメモリに入る前に: core dump を無効化し、`umask` を
`0077` に設定し（SQLite は `-wal` と `-shm` をデータベースのモードではなく
プロセスの umask で作ります）、ペイロードの代わりに固定の文言だけを出す
panic フックを入れます。

リリースプロファイルでは意図的に `panic = "abort"` を**設定していません**。
一見そのほうが安全に思えますが、ここでは逆です。abort は巻き戻しを飛ばし、
巻き戻しを飛ばせば `Drop` が走らず、すべての消去が行われません。

## 保存場所

| | |
|---|---|
| Linux | `$XDG_DATA_HOME/neko-auth/`（既定は `~/.local/share/neko-auth/`） |
| macOS | `~/Library/Application Support/neko-auth/` |
| Windows | `%LOCALAPPDATA%\neko-auth\` |

Windows で `%APPDATA%` ではなく `%LOCALAPPDATA%` を使うのは意図的です。
ローミングプロファイルはログイン時にドメインサーバーへ複製されるので、
保管庫が既定でネットワークを渡り歩くべきではありません。

`--vault <パス>` または `NEKO_AUTH_VAULT` で上書きでき、`NEKO_AUTH_HOME` は
ディレクトリごと移動します。

Unix では保管庫、その付随ファイル、すべてのエクスポートが `0600` になります。
グループや全ユーザーから読める保管庫は起動時に警告します —— モードビットを
失ったアーカイブから復元した、という事態はこうして見つかります。Windows には
モードビットがなく、`%LOCALAPPDATA%` の既定 ACL がすでに本人・SYSTEM・
Administrators に制限しています。DACL を手書きしても、ローカルの管理者に対する
守りにはならず、危険を増やすだけです。

**保管庫を Dropbox、iCloud Drive、OneDrive に置かないでください。** 使用中の
SQLite ファイルと同期クライアントの組み合わせは破損製造機です。neko-auth は
先行書き込みログが有効にならないときに警告しますが、それが典型的な兆候です。
保管庫はローカルディスクに置き、バックアップは `export encrypted` を使って
ください。

## 更新

```bash
neko-auth update --check
neko-auth update
```

ネットワークに触れる唯一のコマンドです。起動時のチェックもテレメトリーも
ありません。「あなたのマシンから出ない」ことを売りにするツールが、どれくらいの
頻度で使われているかをサーバーにこっそり伝えるべきではないからです。

ダウンロードは二重に検証します。まずバイナリに埋め込まれた公開鍵で、
チェックサムファイルの Ed25519 署名を検証し、次にそのファイルに書かれた
SHA-256 でアーカイブを検証します。チェックサムだけでは、配信した相手からバイト
が壊れずに届いたことしか証明できません。GitHub アカウントが乗っ取られても
なお成り立つのは署名のほうです。署名鍵が組み込まれていないビルドは、新しい
バージョンを報告はしますが、インストールは拒否します。

取得元のリポジトリは `config update_repo <owner>/<repo>` で設定するか、
ビルド時に `NEKO_AUTH_REPO` で指定します。

## 壊れたときの復旧

```bash
neko-auth doctor
```

SQLite の整合性チェックを行い、保管庫の署名を検証し、そのうえで全アカウントの
復号を試して、**失敗したものを名指しで報告しつつ、それ以外は動いたままに
します**。この最後の一点こそ、ファイル全体ではなく項目ごとに暗号化することの
実際的な見返りです。ファイル全体を暗号化していると、悪い場所に壊れたページが
一つあるだけで保管庫全体が開かなくなります。

## 開発

```bash
cargo test                       # 単体テストと統合テスト
cargo test --no-default-features # 最小構成のビルド
cargo clippy --all-targets
```

TOTP の実装は RFC 4226 と RFC 6238 の公式テストベクターで検証しています。
SHA-256 と SHA-512 の場合も含みます —— これらは長さの違うシードを使い、
20 バイトの SHA-1 用シードを三つとも使い回すのがこの領域の定番の誤りで、
もっともらしく見えて実際には誤ったベクターを生みます。

セキュリティ上の主張には、それを直接述べるテストがそれぞれあります。暗号文の
どの 1 バイトを反転しても拒否されること、シークレットを別のアカウントの行へ
移すと復号できないこと、表示されるカラムへ移しても復号できないこと、保存された
KDF パラメーターを弱めると鍵のラップが壊れること、行を削除すると保管庫の署名が
検出すること、ツールが書くすべてのファイルが `0600` であること、そしてアドレス
とパスワードの区切りを付け替えても同じ鍵にはならないこと。

翻訳にもテストがあります。すべての言語で引数が正しく差し込まれること、数を
数える語句が英語では変化し他の言語では変化しないこと、繁体字の項目が大陸では
なく台湾の語彙を使っていること、そして中国語と日本語の文中で数字と文字のあいだ
に空白が入ることです。
